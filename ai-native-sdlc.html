CS课程定位与结构

面向对象、前置条件、学完能做到什么，以及 14 课的阶段归属。

面向对象

已经在用 Claude Code、但审批门禁、评审和交接仍以人的速度运行的工程、平台与安全负责人。课程明确写给大型企业，尤其是受监管企业——那里既不允许评审队列堆积，也不允许代码在评审不足的状态下上线。各 play 假定你有权改动组织的规划、评审、测试、部署方式，而不只是写代码的方式。

前置条件

日常能熟练使用 Claude Code，并且拥有一个你有权改动的 Git 仓库与 CI 流水线。每个 play 在「上手准备」一节各自声明自己的前置条件，其中若干个没有前置条件。

学完能做到

  • 解释为什么当 agent 写掉大部分代码后，规划、评审、测试、部署会成为瓶颈，以及它们为何仍以人的速度运行
  • 把一个想法捕获为 intent.md——一个短小、纳入版本控制的文件，声明要什么、为什么要、在什么约束下——并在一次与 Claude 的工作会话内把它变成需求与设计规格
  • 把机构知识维护为纳入版本控制、机器可读的 CLAUDE.md 文件与 skills
  • 在实现过程中穿插持续 evals，配合分层的 agent 评审，把人工评审留给受监管代码与关键代码
  • 在 AI 行动的当刻强制治理，用 hooks 作为审批门禁，并把被突破的控制带写回为新的 intent.md 以闭环

引言

01引言

各组织已经开始用 AI 以一年前无法想象的速度写代码，然而围绕代码的那些流程并没有以同等速度改变。

许多工程团队仍在沿用原来那套审批门禁、评审、交接和策略，这拖住了使用 Claude Code 这类 agent 化编码方案本应带来的生产力提升。

传统 SDLC

软件开发生命周期（SDLC）是把软件从想法送到生产环境的那套流程。多数组织跑的都是同样六个阶段的某个版本，覆盖规划、设计、构建、测试、部署与维护。传统做法下，每个阶段都是一个独立环节，由不同角色负责：产品经理写需求，技术架构师把需求转成设计，工程师实现设计，受监管企业里的 QA 团队验证软件，发布团队把它上线，运维监控在跑的东西。工作通过文档、工单和签署确认在各环节之间流转。

传统 SDLC 流程厚重，目的是确保每一步都有问责和管控。但传统 SDLC 是为这样一个时代设计的：最耗时、最昂贵的阶段是编写和实现代码——而今天已不再如此。产品需求文档（PRD）、估点仪式、产品安全评审，这些都是为了在可能长达数周、数月甚至数季度的开发工作中强行对齐而存在的。

传统 SDLC 还有一个特征：它的控制项假定每一步都由人来做。产出价值最高的那些组织，已经围绕 agent 化 AI 如今的能力重建了自己的流程，同时确保人始终在闭环之中。在本手册中，我们逐一介绍我们 Applied AI 团队在 SDLC 各阶段内部集成 Claude 的若干最佳实践，用以加速开发、让流程跑得更快——这些实践源自我们与客户合作的经验。

当代码不再是瓶颈

当代码不再是瓶颈、构建阶段跑得比传统 SDLC 所能容纳的更快时，三件事随之成立：

  1. 瓶颈转移到构建阶段两侧的环节——主要是规划、评审/测试和部署，它们仍以人的速度运行。
  2. 控制项不再匹配现实，变得难以为继。当代码由人写时，逐行手工评审是合理的；一旦 agent 写掉大部分 diff，这种做法就跟不上了。
  3. 治理成本上升，因为例外情况仍要走每周或每月才开一次的会议和委员会。
配图说明：瓶颈发生了转移——构建阶段收缩到 agent 的速度，而它周围的阶段仍以人的速度运行。

拿安全瓶颈举例。安全团队的人员编制是按人的产出规模来定的，所以当 agent 把代码产出翻倍时，要么评审队列堆积，要么代码在评审不足的状态下上线。受监管的组织两个结果都不能接受，因此它的安全与策略检查必须跟上 agent 的节奏。

要更好地兑现 agent 化 AI 的生产力收益并保障其安全，传统 SDLC 需要经历与实现阶段同等程度的转型。

什么是 AI 原生 SDLC

AI 原生 SDLC 是一套重新构想的流程，它把原有的控制目标与新的强制手段结合起来。流程不再是线性流转，而是变成一个循环，AI 嵌入其中每一个环节。AI 原生 SDLC 推动自动化的交接与后续 play 的自动触发，从而缓解传统 SDLC 各阶段之间手工、笨重的交接问题。

play 如何运作

play 是本手册的核心，被归入六个非线性阶段（规划、设计、构建、测试、部署、维护），合起来覆盖完整生命周期。每个 play 覆盖：

  • 发生了什么变化
  • 上手准备
  • 落地的具体步骤
  • 治理考量
  • 如何度量它是否奏效

各 play 是模块化的，组织可以根据自身需要，在不同时期优先转型不同阶段。每个 play 在「前置条件」下声明自己的依赖，依赖关系图对此有进一步说明。

一个阶段以提交一份产物结束，而这次提交就启动下一个阶段。被接受的 intent.md 触发需求与设计环节，获批的 spec.md 触发 plan mode，合入的 PR 触发流水线，生产环境中被突破的控制带写出下一份 intent.md——循环由此继续。

规划intent.md→ 设计spec.md→ 构建plan.md + diff→ 测试evals→ 部署PR + hooks→ 维护控制带突破↻

起初你需要手工提示每一步；终态则是一个循环：每份被接受的产物都点燃下一道门禁。人的注意力集中在门禁处，评审 agent 标记出来的东西，而不是从零开始每个阶段。

Stage 1 规划

02捕获为 intent.md

intent.md 启动整个软件开发流程，它可以由不同路径进入：有人有了一个想法、有人提了一张工单，或者某个事件通过告警被暴露出来（见 Stage 6 维护）。

当一个人有了想法时，他与 Claude 一起头脑风暴，产出一份 Markdown 原型规格。而在传统 SDLC 里，同一个人接下来还必须说服产品团队的某位成员，与他一起、或者代他把这个想法写成文档。

Claude 生成的这份原型规格人类可读、纳入版本控制，且下一个阶段可以立即消费。它以 intent.md 的形式保存。

无论 intent 源自事件触发还是源自某个人，步骤都相同：产品负责人在它被提交之前，评审并修正这份由 agent 撰写的 intent.md。

发生了什么变化

传统做法AI 原生做法
一个想法要先经过待办条目、用户故事、故事点和细化会议，才有人能对它动手。每次交接都发生一次归属权转移，所以最终到达工程团队的东西，与提出者原本的意思已经隔了好几层。 提出者与 Claude 头脑风暴，把结果写成 intent.md——一份用提出者自己的话写成的原型规格。该产物包含要什么、为什么要、在什么约束下。重复性流程则编码为 skills。

上手准备

前置条件：无

基础设施：为非工程人员提供的 Claude 访问权限（claude.ai 或 Cowork）；一份约定好的 intent.md 模板；一个共享的、纳入版本控制的 intent 存放处，由产品负责人关注。对单一产品而言，最简单的存放处就是产品仓库里的一个 intent/ 目录。这样安排能让产物链紧邻由它派生出的代码。只有当 intent 横跨多个仓库时，专设一个 intent 仓库才值得那份额外开销；在 monorepo 里它就是一个目录。Stage 3 构建中的「遗留系统」一节讲了这个存放处与已经持有记录的 Jira 或需求管理工具之间的关系。

搭建这套东西对平台团队或工程团队是一次性任务。需要一位技术团队成员把 intent 存放处立起来，并决定谁有写入权限，因为贡献者会来自整个组织。

仓库一旦存在，没有 Git 经验的贡献者并不需要直接使用 Git。取而代之的是：一个连到版本控制系统（例如 GitHub）的连接器，让 Claude 能从 claude.ai 或 Cowork 代他们提交 Markdown 文件。

怎么执行

  1. 提出者用自己的话向 Claude 描述问题。他可以描述今天做不到什么、这个想法影响到谁、更好的状态是什么样、什么不在范围内。不需要任何正式语言。
  2. 头脑风暴，直到想法变得具体。Claude 会问一位分析师会问的那些问题：范围、用户、约束，以及成功长什么样。
  3. 请 Claude 按组织的模板把结果写成 intent.md。该模板可以编码为一个 skill，由技术团队成员搭建、由负责人签署确认，内容可涵盖问题、期望结果、受影响的用户与系统、约束，以及待解决的问题。
  4. 提出者修正 Claude 理解错的任何地方。
  5. 把 intent.md 提交到共享存放处。作者和时间戳随之进入记录，产品负责人从这里接手这个想法。

治理考量

证据就是那份已提交的 intent.md，它记录了作者、时间戳和完整修订历史，并留痕在 intent 存放处的 Git 历史里。产品负责人批准；把该 intent 送入 Stage 2 设计 的接受或拒绝决定，则以合入或关闭评审的形式被记录下来。

怎么度量

领先指标

从第一次对话到 intent.md 被提交所花的时间，从 intent 存放处的 Git 历史读取（其中记录了作者与时间戳）。预期是从长达数周的需求获取与细化周期降到数小时。

滞后指标

存活率，即产品负责人接受进入 Stage 2 设计（而非关闭）的 intent.md 占比。接受或拒绝的决定以产物被合入或评审被关闭的形式记录。此外，统计同一变更在首个 spec.md 提交之后对 intent.md 所做的改动次数。

Stage 2 设计

03需求与设计

产品负责人一旦批准了 intent.md，Claude 就取用它并产出一份需求与设计规格。这个过程由组织在品牌、安全、合规和 UX 方面的 skills 引导。

产品负责人评审这份规格，但不撰写它。这个流程的目标是产出一份工程团队可以据以规划的规格，其中标记出了需要关注的地方。

前端工作是最清晰的例子。intent.md 一旦被接受，产品负责人就依据它在 Claude Design（beta）里把设计稿做出来，在稿子上迭代，然后导出给 Claude Code 去实现。

发生了什么变化

传统做法AI 原生做法
需求和设计是由不同团队负责的两个独立环节。分析师把想法形式化为需求，设计师再把需求反向解析成设计。这种分离是为了问责而存在的，但它既慢又有损耗。 两个环节在一次被提示的会话内完成。Claude 取用 intent.md，产出一份需求与设计规格，受组织的 skills 约束，并标记出需要关注的地方。

上手准备

前置条件：写好一份 intent.md品牌 / 安全 / 合规 / UX 策略已写成 skills

基础设施：一位拥有 Claude 访问权限的产品负责人。不需要工程技能。

怎么执行

  1. 产品负责人开启一个会话，其中组织的 skills 可用，并附上 intent.md。
  2. 产品负责人的提示词指向该 intent、点明各项约束、并要求标记出关注点。一开始手工跑；随后把它固化为一个组织级的斜杠命令。再往后，把 intent 存放处中 intent.md 被接受这一动作设为触发器：一个非交互作业在合入时触发，加载组织的 skills 跑完这一环节，并以拉取请求的形式提交 spec.md（Stage 5 部署 中的 CI/CD play 讲了这套管路）。从那时起，产品负责人第一次介入就是评审。
  3. 同一位产品负责人对照原始想法评审这份规格。规格是否解决了所陈述的问题？intent.md 中那些待解决的问题是被回答了，还是被延续下去了？
  4. 优先处理被标记出来的关注点，因为那些正是一位分析师本会向上升级的地方。产品负责人在工程团队看到规格之前，与各自的策略责任人逐一解决它们。
  5. 把 spec.md 与 intent.md 并排提交。这一对文件记录下了「当初要求什么」和「最终决定了什么」。
  6. 产品负责人决定这份规格和 intent 是否进入构建阶段，对组织认定为较高风险的任何事项则咨询技术负责人。这个决定始终由人类同事来做；而接受该规格，正是启动 Stage 3 构建 中 plan mode play 的动作。

长什么样

提示词：

prompt 
Read the attached intent.md and produce a requirements and design spec
for integrating it into our existing codebase. Apply the skills available
to you so the plan conforms to our brand guidelines, security policies
and UX standards. Document the spec fully as spec.md, ready to hand to
the engineering team. Describe clearly any areas of concern, especially
where you cannot satisfy contradicting policies.

治理考量

策略冲突不再是数周后在某次评审中才被发现，而是在规格被撰写的当刻就读取并应用了当下生效的策略。组织的 skills 作为约束施加在规格之上。规格本身、产出它的提示词，以及当时生效的 skill 版本，全部留痕在版本控制中。产品负责人对规格签署确认，并把被标记的关注点路由给指定的策略责任人。

怎么度量

领先指标

同一变更的 intent.md 提交与 spec.md 提交之间的耗时（两个 Git 时间戳之差），与原先「需求 + 设计」周期作对比。

滞后指标

构建启动之后的需求返工量。统计同一变更中日期晚于首个 plan.md 提交的 spec.md 提交数。git log 可以直接给出这个数字。

Stage 3 构建

04以 Claude Code 的 plan mode 作为默认起点

工程师在 plan mode 下启动 Claude Code 会话，把 Stage 2 设计 阶段获批的 spec.md 交给 Claude，让它反过来访谈自己，在计划上反复迭代直到满意。

发生了什么变化

传统做法AI 原生做法
工程师读完设计就开始写代码。这次变更具体怎么做——细到改哪些文件、写哪些测试——留在工程师脑子里，最好的情况也只是留在某条工单评论里。没有别人能评审它。评审者看到的第一样东西是成型的 diff，而到那时返工已经很慢了。 工作从一份书面计划开始，由 Claude 在 plan mode 下产出——该模式下它能读代码库但不做任何改动。工程师在代码被写出来之前修正计划，获批的版本作为 plan.md 提交，供后续阶段据以核对。

上手准备

前置条件：如果已有 intent 产物（intent.md 或 spec.md）则用上它CLAUDE.md 文件也有帮助

基础设施：拥有该仓库访问权限的 Claude Code。

怎么执行

  1. 工程师在 plan mode 下与 Claude 开启会话。
  2. 工程师把 intent.md 和 spec.md 交给 Claude，要求一份实现计划，其中点明会改动哪些文件、工作的先后顺序，以及能证明它成立的那些测试。
  3. 拷问这份计划：问这次变更可能弄坏什么、哪一步风险最高、Claude 考虑过但选择不做的其他方案有哪些。
  4. 反复迭代，直到一位从未看过这段对话的工程师，仅凭这份计划就能实现该变更。
  5. 把获批的计划作为 plan.md 提交。该计划加入审计轨迹，而 PR 评审 play（Stage 5 部署）会拿最终的 diff 与它核对。
  6. 接受计划，让 Claude 去实现。有一份扎实的计划，实现往往一遍就过。
  7. 当实现偏离了计划时，在同一次提交中更新 plan.md。可以考虑用一个 hook 来强制两者保持同步。

长什么样

plan.md：

markdown · plan.md

portal/src/claims/StatusPanel.tsx (new), claims-api/routes/status.py, claims-api/tests/test_status.py

## Order of work

1. Add the status endpoint behind existing auth.
2. Panel against the endpoint.

治理考量

设计评审发生在任何代码被生成之前——那时改变方向还只是编辑一份文档的事。plan mode 自身就强制了这一点，因为在工程师接受计划之前，Claude 无法编辑文件。计划及其各次修订，连同是谁接受了它，一并留痕。常规变更由工程师批准；组织认定为较高风险的任何事项则交给技术主管或架构师。

怎么度量

领先指标

一次实现即合入的变更占比，以及从计划获批到 PR 合入的时间（所需数据都在 PR 元数据里）。

滞后指标

每个变更的返工轮次（同样取自 PR 元数据），以及合入的 diff 仍与已提交的 plan.md 相符的频率。

Claude Code 的 auto mode

Claude Code 也可以在 auto mode 下运行：工程师迭代并批准计划，随后 Claude 逐项应用每处改动，不再逐次编辑都来征求许可。随着后续各 play 带来的护栏成熟起来（调优过的 CLAUDE.md、把策略编码进去的 skills、拦截不安全动作的 hooks，以及一套 Claude 能自己跑的测试），auto mode 会成为常规工作的默认模式：一份严谨的 spec.md、一个小的影响面，以及已被测试覆盖的代码。

这个转变的方向，是从「用户盯着 agent 逐个做编辑并评审这些动作」，转向「在较长的自主会话之后评审产物」。auto mode 配合 worktrees 使用时，还能进一步支撑个人与团队层面的并行，并且是自主运行 SDLC、闭合循环（如 Stage 6 维护 所述）的基础。

遗留系统与事实来源

现有的 SDLC 流程很可能已经在追踪各类产物了，只是没有以 Markdown 文件的形式。工作项可能在 Jira 里，需求在某个内置了合规可追溯性的工具里，设计在 Figma 里，变更审批在某个变更委员会那里。这些系统很难被取代，因为审计师和监管方已经接受了它们，并且其他团队依赖它们——所以 AI 原生 SDLC 必须适配既有现实。对流程产出的每一类产物，应当指定其中一个系统为事实来源，其余系统持有副本或链接。

以下几种配置都能做到「只有一个事实来源」，而具体选哪种可以因产物而异：

  • 以仓库为事实来源。 Markdown 产物是权威记录，遗留系统在提交中引用这些文件。对工程主导的组织，这可能是最干净的配置之一，因为所有记录都活在一个工具里、只有一个时间戳权威。
  • 以遗留系统为事实来源。 Jira、ServiceNow 或需求管理工具持有权威记录，Markdown 产物是工作副本。Claude 在会话开始时读取该记录，并在产出规格或计划的同一个会话内，通过 Model Context Protocol（MCP）连接器把结果写回去。
  • 以建立链接为最低标准。 所有产物都记下记录 ID，所有遗留记录都包含对应 Markdown 文件的提交 SHA。当存在两个事实来源时，链接这一选项是转向 AI 原生 SDLC 的一个好起点。

只要两者之间存在链接，或者其中一个被宣告为事实来源，遗留系统与 AI 原生的 Markdown 优先体系就可以共存。

Stage 3 构建

05CLAUDE.md

CLAUDE.md 把一位新人所需的上下文交给 Claude，涵盖约定、命令、架构，以及团队最常遇到的那些错误。原本存在于人脑中和 wiki 上的知识，变成一个 agent 在每次会话开始时都会读取的文件，由整个团队共同维护，每犯一次错就迭代一次。

上手准备

前置条件：无

基础设施：一个仓库、已安装的 Claude Code，以及一位熟悉该代码库的工程师。

怎么执行

  1. 在仓库里运行 /init。Claude 会依据它发现的内容生成一份初始 CLAUDE.md。
  2. 把生成的文件削减到「一位新人第一天所需」的程度。保留构建、测试和 lint 命令，真正重要的那些约定，以及 Claude 反复搞错的那些点。
  3. 把 CLAUDE.md 提交到 Git 的仓库根目录，这样整个团队共用同一个版本，对它的改动会像代码一样被评审。
  4. 有一条实操规则很有用：当 Claude 第二次犯同一个错误时，把纠正写进 CLAUDE.md。
  5. 把它控制在一页以内，因为 Claude 在会话开始时会读完全文，任何过时内容都在白占上下文而不带来任何收益。

长什么样

CLAUDE.md：

markdown · CLAUDE.md 
# Payments service
## Commands
- Build: make build
- Test: make test (unit), make itest (integration, needs docker)
- Lint: make lint (runs in CI; fix before pushing)
## Conventions
- Java 21, Spring Boot 3. No new Lombok.
- Money is always BigDecimal, never double.
- Every endpoint needs an integration test in src/itest.
## Architecture
- api/ holds REST controllers, core/ holds domain logic,
  adapters/ talks to external systems.
- Kafka events are defined in schemas/; never edit generated classes.
## Things Claude gets wrong
- Do not bump dependency versions; the platform team owns them.
- The legacy v1/ package is frozen; changes go in v2/.

治理考量

CLAUDE.md 纳入版本控制，因此 agent 所遵循的指令是可评审、可审计的。团队约定通过该文件生效，对它的改动留痕在 Git 历史里，代码所有者在 PR 评审中批准这些改动。

怎么度量

领先指标

Claude 重复犯本该被 CLAUDE.md 拦住的错误的频率。对 CLAUDE.md 的纠正或改动应当在 Git 历史中被追踪。

滞后指标

团队新成员从加入到首个 PR 合入的时间，取自 PR 历史。

Stage 3 构建

06用 skills 承载机构知识

skills 是组织把机构知识变得可操作的方式。其中的指令是显式的、纳入版本控制的、被广泛应用的，并在策略变更时集中更新。

经验法则

必须被一致应用的机构知识，写成 skill；属于 CLAUDE.md 或提示词的那些成分，不要写成 skill。

上手准备

前置条件：无硬性要求有 CLAUDE.md 会有帮助，但 skill 并不依赖它

有 CLAUDE.md 会有帮助，因为它把 agent 的工作知识留在仓库里，但 skill 并不依赖它。

基础设施：一条有指定责任人、且有书面事实来源的策略。

怎么执行

  1. 挑一项今天执行得不一致的知识。可以是一条安全标准、一项 API 设计约定，或者一条品牌规则。
  2. 把它写成一个 skill——一个包含 SKILL.md 的目录，其 frontmatter 声明何时触发，正文声明要做什么。由工程师依据策略责任人的事实来源撰写，可借助 Claude。
  3. 把该 skill 放在仓库的 .claude/skills/<name>/ 下，使它随代码一起分发；或者通过插件在全组织范围分发。
  4. 测试该 skill 会被触发。用不同的问法请 Claude 做相关任务，确认每次它都加载了该 skill。
  5. 当策略发生变更时，改这个 skill，并让策略责任人对该改动签署确认。
  6. 工程师在下一次会话中自动获得新版本。

长什么样

.claude/skills/secure-api-review/SKILL.md：

markdown · SKILL.md 
---
name: secure-api-review
description: Apply the API security standard. Use whenever creating or
  modifying an external-facing endpoint, reviewing API code, or
  generating an OpenAPI spec.
---
# Secure API review
When you create or change an API endpoint:
1. Authentication: every endpoint requires the gateway JWT;
   no anonymous routes outside /health.
2. Input validation: validate request bodies against the OpenAPI
   schema and reject unknown fields.
3. Audit: every state-changing endpoint emits an audit event with
   actor, action, entity and timestamp.

   appear in logs or error messages.

治理考量

skill 是一项控制项，但属于建议性控制。它让 Claude 在代码被撰写的当刻很可能应用该策略，但没有任何机制强制某次会话必须遵守它。一条必须始终成立的策略，背后需要某种确定性手段来托底，比如一个拦截该动作的 hook，或者在 PR 处重新核查该策略的一道评审环节。

skill 让违规变得罕见，hook 让违规接近不可能。

skill 的调用留痕在会话轨迹里，策略责任人像评审代码那样评审 skill 的改动。

怎么度量

领先指标

从策略责任人批准某项策略变更，到更新后的 skill 被合入所花的时间，取自该 skill 目录上的 PR。

滞后指标

引用了该策略的 PR 评审发现项数量。一旦 skill 在代码被撰写的当刻就在应用该策略，这个数字应当趋近于零。若它没有趋近于零，那么要么该 skill 没有被触发，要么它的文本已经偏离了正式策略。

hooks 作为构建期护栏

skill 是建议性控制，而 hook 是它背后的确定性层。Claude 的大部分动作是实现过程中的文件编辑与 shell 命令，所以构建阶段往往是 hooks 触发最频繁的地方。

构建期 hooks 可以：

  • 拦截对受保护路径的编辑，例如生成的类文件或某个已冻结的包
  • 在文件编辑之后运行格式化器和 linter，使偏移永不累积
  • 让凭据不进入 diff
  • 为任何必须无例外成立的 skill 策略托底

hook 会在每一个匹配它的动作上运行，因此构建期 hooks 应当快速，且作用范围限定在发生改动的那个文件上。更重的检查（例如整套测试）应放在提交处或 PR 处。

那种要求人来批准的 hook，属于 Stage 5 部署 里的门禁，因为在构建过程中弹出审批提示，等于把一个人重新放回所有并行会话的关键路径上。

Stage 3 构建

07并行会话与子代理

一位工程师可以同时驱动多条工作流。

并行会话是另一个完整的 Claude Code 实例，在它自己的 Git worktree 里处理一个独立任务。各个独立会话彼此毫不知情，它们唯一共享的东西就是那位在操控它们的工程师。

子代理运行在单个会话内部，是一个作用范围受限的助手，拥有自己的上下文窗口和工具限制，适合那些在多个任务中反复出现的活儿，例如验证应用是否按预期运行。

并行会话提高了一位工程师能同时推进的任务数量，而子代理让每个会话专注于它自己的任务。工程师的工作是操控并评审它们全部。

发生了什么变化

传统做法AI 原生做法
一位工程师一次做一个任务，并把一天/一周中相当一部分时间花在构建、测试和评审上。等待期间切换到别的任务是可行的，但上下文切换足够累人，以至于很少有人愿意这么做。 一位工程师同时运行多个 Claude 会话，每个都在自己的 worktree 里做自己的任务。反复出现的活儿变成子代理，各有自己的上下文和工具限制。工程师的工作转向编排，并最终转向构建与监控各种循环。

上手准备

前置条件：CLAUDE.md（所有会话都会读取）反馈闭环（Stage 4 测试）有帮助

反馈闭环（Stage 4 测试）在这里也有帮助，因为当一个会话能验证自己的工作时，工程师需要的监督就更少。

基础设施：一个 Git 仓库，因为隔离性来自 worktrees；以及调优过的权限设置，使会话不会因为组织认为安全的命令而卡在审批提示上。

怎么执行

  1. 工程师把工作拆成触及不同文件的任务，借助 plan mode play（Stage 3 构建）产出的计划来看清哪些工作是相互独立的。共享文件的任务放在同一个会话里，一个接一个地做。
  2. 每个并行任务分到它自己的 worktree，例如在一个终端里 claude --worktree feature-auth，在另一个终端里 claude --worktree fix-rate-limit。worktree 是一份独立的检出，位于自己的分支上，这能阻止会话之间在文件上相互碰撞。
  3. 两三个会话是一个合理的起点。实际上限是一个人能否妥善评审这么多条流，所以只在评审跟得上的前提下增加会话数。
  4. 把反复出现的活儿变成子代理，以 Markdown 文件定义在 .claude/agents/ 中，每个都有名字、何时使用它的说明，以及它可以触及的工具。例子包括：一个在主 agent 完成后剥离多余复杂度的代码精简器；一个运行应用并检查行为的验证器；一个探索代码库并回报结论、而不把主上下文淹掉的调研器。把这些定义提交到 Git，使整个团队共用它们。

长什么样

.claude/agents/verifier.md：

markdown · verifier.md 
---
name: verifier
description: Runs the app and checks the change works before the session reports done
tools: Bash, Read
---
Start the app with make run. Exercise the changed behavior and the two
nearest neighboring flows. Report what you ran, what you saw, and any
behavior that does not match plan.md. Do not fix anything; report only.

治理考量

会话更多意味着产出更多，所以控制项必须来自仓库里的配置。仓库中的 hooks 和权限设置对所有会话生效，而某个会话做了什么会被记录，并归属到运行它的那位工程师名下。

怎么度量

领先指标

在评审质量得以保持的前提下，每位工程师的并发会话数（从 OpenTelemetry 导出数据统计），以及一天中用于操控（而非等待）的时间占比。

滞后指标

每位工程师每周合入的变更数，与返工率并读（返工率按 PR 历史确定）。

Stage 4 测试

08给 Claude 一个反馈闭环

始终给 Claude 一条能验证自己工作的途径，无论是测试、构建，还是截图比对。让一个会话在工程师看到之前，先检查自己的工作、修掉自己的错误。

反馈闭环不应与验证子代理（Stage 3 构建）混为一谈

反馈闭环贯穿整个任务，按工作所需运行任意多次。而验证子代理是打包最终检查的一种方式：在会话认为工作已完成之后，用一个全新的上下文窗口跑一遍。这样一来，结论就不会被产出这些代码的那些假设所染色。

发生了什么变化

传统做法AI 原生做法
「代码可用」这个信号来得很晚：CI 是几分钟后，测试人员是几天后，生产环境是几周后。当代码由 agent 产出时，信号来得晚就意味着必须由人来检查它的全部输出，而那个人就成了瓶颈。 给会话一条在人看到之前检查自己工作的途径：跑测试、跑构建、截图。Claude 反复迭代直到检查通过，所以到达工程师手上的东西已经通过了这道检查。搭建这个闭环由运行该会话的工程师负责，下面的步骤就是写给他的。

上手准备

前置条件：无

基础设施：一套测试和一次构建，各能用一条命令在本地跑起来。对 UI 工作而言，让 Claude 能看见结果至关重要——要么是一个浏览器工具，要么是通过 MCP 接进来的截图工具。

怎么执行

  1. 如果今天检查这项工作需要一串命令加上一些环境知识，就把它包成单一目标，例如 make test 或 npm test，并在失败时以非零码退出。
  2. 在 CLAUDE.md 的 Commands 一节，逐条列出每个命令，并附上一个健康输出的示例。
  3. 陈述一个目标，并让它可量化，这样 Claude 无需询问你就能检查工作。例如：「test_status.py 中所有测试通过」、「截图与所附设计稿一致」，或者「该端点返回 200 且带上新字段」。
  4. 修 bug 时，先写那个会失败的测试。请 Claude 把该 bug 复现为一个测试、跑它，并确认它失败的原因正是你预期的那个原因。提交这个测试。只有到这一步之后，才请 Claude 在不编辑该测试的前提下让它通过——最后一步提到的测试文件 hook 会强制这项限制。一个在修复之前就已存在、且 agent 无法改写的测试，才是该 bug 已消失的证明。
  5. 对 UI 工作，用视觉检查闭合这个环。给 Claude 一个浏览器或截图工具，给它设计稿，让它迭代：实现、截图、比对、调整。两三轮是正常的，且每一轮结果都应更好。
  6. 把验证纳入「完成」的定义。这条指令写在 CLAUDE.md 里：「在报告任务完成之前先跑测试，并展示输出。」
  7. 最后，这个闭环本身也需要被保护，因为一个正在修代码的 agent 绝不能有能力削弱对那段代码的检查。一个在修复任务期间拦截对测试文件编辑的 hook 就能做到这一点。替代方案是在评审中检查 diff，并拒绝任何触及测试的改动。

长什么样

CLAUDE.md 的验证段落：

markdown · CLAUDE.md 验证段落 
## Verifying your work

- Build: make build (must finish with "Build succeeded")
- Test: make test (all green; never skip or delete a failing test)
- Lint: make lint (zero warnings)

Run all three before reporting any task complete, and paste the output.
If a test fails, fix the code, not the test.

治理考量

  • 强制了什么：任务报告完成之前必须验证，以及在修复期间禁止 agent 编辑测试文件——组织希望这两点得到保证时，都以 hooks 实现。
  • 证据是什么：make test 的字面输出、构建日志，或者 Claude 跑出并粘贴的截图比对结果。也就是说，证据来自工具链本身。
  • 留痕在哪里：留痕在会话轨迹中（由 OpenTelemetry 导出转发到组织的可观测性栈），以及 PR 的检查运行中——评审者和日后任何审计方都能看到它。
  • 谁批准：评审该 PR 的代码所有者。因为机械性的证据已经附上，他可以专注于意图与风险。

怎么度量

领先指标

agent 所写变更的 CI 一次通过率，这是 CI 系统本就支持的数据。

滞后指标

每个 PR 的评审时长（取自 PR 元数据）——一旦测试接住了原本靠评审者接住的问题，它应当下降；以及来自事件追踪系统的变更失败率。

Stage 4 测试

09在 CI 中持续跑 evals

evals 是阶段门禁式 QA 在 AI 原生体系下的对应物。落到实处，它是一套在 agent 的配置发生变更时就运行的评测套件。当换入一个新模型、或者某段提示词被改写时，eval 套件会告诉你该 agent 是否仍以同样的标准完成工作。

evals 应当被视为一套活的套件。随着模型能力提升，曾经具备区分力的用例会失去区分力，而持续监控中浮现的新用例必须被补进来。

视具体用例而定，有些团队可能更倾向于按固定节奏离线跑这些 evals，而不是每次变更都跑。下面的步骤针对的是持续评测。

上手准备

前置条件：CLAUDE.md反馈闭环（Stage 4 测试）

基础设施：能以非交互方式运行 Claude Code 的 CI，以及一个有预算跑 eval 的 API key。

怎么执行

  1. 平台工程师从近期工作中收集 20 到 50 个真实任务，每个都带上其预期结果或已被接受的结果。
  2. 把每个任务写成一个 eval，也就是提示词加上定义「可接受」的那些检查（测试通过、lint 干净、行为未变、策略被遵守）。
  3. 该套件在 CI 中以非交互方式运行：按计划定时运行，以及在 CLAUDE.md、skills 或 hooks 发生任何变更时运行——因为这些配置在操控 agent，理应享有代码所享有的回归测试。
  4. 把配置变更卡在结果上。一处降低了通过率的 skill 变更，在合入之前要先被评审。
  5. 每一次生产事故都产出一个 eval，由拥有该事故的团队撰写，并作为回归测试常驻在套件中。

长什么样

.github/workflows/agent-evals.yml：

yaml · agent-evals.yml 
name: Agent evals
on:
  pull_request:
    paths: ['CLAUDE.md', '.claude/**']
  schedule:
    - cron: '0 2 * * *'
jobs:
  evals:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm install -g @anthropic-ai/claude-code
      - name: Run eval suite
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          for eval in evals/*.json; do
            claude -p "$(jq -r '.prompt' $eval)" \
              --allowedTools "Read,Edit,Bash(make test)" \
              --output-format json > result.json
            ./evals/check.sh "$eval" result.json
          done

治理考量

evals 给了 QA 一道能跟上 agent 产出速度的门禁。通过率阈值以合入检查的形式强制执行，各次运行都留痕以便结果能跨时间比较，而拥有该配置变更的团队负责批准它。

怎么度量

领先指标

eval 通过率随时间的走势（套件每次运行都会报告），以及一次生产事故要多久才变成一个常驻 eval。

滞后指标

在 CI 中被接住的回归数，对比在生产环境中被发现的回归数（后者取自事件追踪系统）。

Stage 5 部署

10让 AI 进入 PR 评审闭环

Claude 既做评审方，也做被评审方。它对照组织的策略评审进来的 PR，也处理针对它自己 PR 的评审意见。这让工程师在 PR 评审中能专注于行为本身，说到底就是判断意图与风险。

发生了什么变化

传统做法AI 原生做法
评审产能是按人的产出规划的。一个 PR 要等某位评审者把它全部读完，评审质量随该评审者的负载而波动，作者一边催一边看待办堆积。 所有 PR 都获得同一套评审环节，发现项按严重度排序。人的注意力上移一个层次：这个变更是否做到了计划所要求的事，以及风险是否可接受。

上手准备

前置条件：已更新的 CLAUDE.md（Stage 3 构建）skills（若要强制成文策略）已定义好的子代理

基础设施：一个已安装 Claude 集成的仓库——要么是由管理员启用的受管 Code Review 服务（研究预览），要么是在你自己的 CI 中运行的 claude-code-action，并在需要时把模型调用走 Amazon Bedrock、Google Cloud 的 Vertex AI 或 Microsoft Foundry（CI/CD play 覆盖了这些部署选项）。要求代码所有者批准的分支保护策略同样值得配上。

怎么执行

  1. 受管 Code Review 服务是启动最快的方式：由管理员启用它并选择仓库。当你需要掌控流水线，或者希望 API 调用走你自己的云合约时，就用 claude-code-action 在自己的 CI 里跑评审（CI/CD play 覆盖了那套管路）。
  2. 技术主管把评审策略写成仓库根目录下的 REVIEW.md，按组织关心的那些环节划分：bug 与逻辑错误；安全与漏洞；对照规格（需求 play 产出的 spec.md）、实现计划（plan mode play 产出的 plan.md）与设计原则的合规性。REVIEW.md 还定义了什么算 Important 而什么只是 Nit，以及什么该跳过。
  3. 技术主管设定人工介入的阈值。发现项本身既不批准也不阻塞 PR，分支保护仍然要求代码所有者的批准。若某位平台工程师希望按发现项来卡合入，可以读取检查运行发布的那份机器可读的严重度计数。
  4. 当某位评审者或作者在一条评审意见上标记 @claude 时，Claude 处理该意见并推送修复。PR 讨论线同时记录下这个请求和这次改动。这个修复闭环通过 claude-code-action 运行；在受管服务里，评论 @claude review 则是请求一次全新的评审。对 Claude 自己开的 PR，可以再往前一步，让 Claude 把这个 PR 一路看护到合入。有些团队把这个闭环包成一个自定义斜杠命令：它清扫该 PR 上未解决的评审意见和失败的检查，逐一处理并推送修复，直到该 PR 全绿、只等代码所有者批准。
  5. 评审发现项反哺回 CLAUDE.md。当某次评审第二次标记出同一个错误时，就在那次评审中把纠正写进 CLAUDE.md；而因为评审会读取 CLAUDE.md，这个错误从下一个 PR 起就会被接住。评审也会指出某次变更已经让 CLAUDE.md 过时了。
  6. 技术主管每月调优一次这套配置：给发现项打分使评审方持续改进，并在 REVIEW.md 里给 Nit 的数量设上限。生成路径以及 CI 已经在强制的东西都排除掉。

长什么样

REVIEW.md：

markdown · REVIEW.md 
# Review instructions
## Passes
Run three passes and tag each finding with its pass:
- Bugs: logic errors, broken edge cases, subtle regressions
- Security: injection risks, authentication gaps, PII in logs
- Compliance: the change matches spec.md, plan.md and our design principles
## What Important means here
Reserve Important for findings that would break behavior, leak data

治理考量

职责分离得以保留，因为写了这些代码的那个 agent 没有任何途径批准它。REVIEW.md 中的评审策略应用于所有 PR，而发现项、修复、评分和批准全部留痕在 PR 历史里——因此 PR 就是那份审计记录。批准来自人，通过分支保护给出，并由发现项提供依据。

怎么度量

领先指标

到首次评审的时间（应当降到分钟级），以及无需人碰分支即被解决的评审意见占比（数据直接存在 Git 上）。

滞后指标

合入前被接住的缺陷与漏洞数，对比逃逸到生产环境的那些（分别取自 PR 历史与事件追踪系统）。

Stage 5 部署

11用 hooks 作为审批门禁

构建阶段把 hooks 当作护栏使用：在无人介入的情况下放行或拦截动作（Stage 3 构建）。而 hook 也可以「询问」——把动作暂停住，直到某个特定的人批准。这正是发布卡口所需要的能力。

hooks 并不专属于部署

这个 play 被放在 Stage 5 部署，是因为发布门禁是最清晰的例子；但 Claude 在哪里行动，它们就在哪里运行。举例来说，hooks 可以在 Stage 3 构建 期间拦截「没有变更工单就修改迁移脚本和基础设施」的行为，也可以在 Stage 4 测试 的修复任务中阻止 agent 编辑测试文件。

上手准备

前置条件：无

基础设施：一份书面清单，列出变更流程所要求的各项审批。

怎么执行

  1. 工程管理层会同变更管理与合规部门，列出那些必须保留下来的人工审批门禁，例如变更管理签署确认、发布授权，以及对受保护路径的修改。
  2. 平台工程师把每道门禁表达为一个 hook——一个在 Claude 行动之前运行的脚本，它可以放行、询问或拦截。
  3. 团队级 hooks 放在 Git 中的 .claude/settings.json 里；不可协商的 hooks 放进由平台或 IT 管理员掌管的受管设置中，个别工程师无法把它们关掉。
  4. 拦截应当自我说明：当一个 hook 阻止了某个动作时，原因和取得批准的途径都要出现在 Claude 的输出里。

长什么样

项目 .claude/settings.json 中的一个独立示例：

json · .claude/settings.json 
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/production-gate.sh" }
        ]
      }
    ]
  }
}

以及门禁脚本本身（.claude/hooks/production-gate.sh）：

bash · production-gate.sh 
#!/bin/bash
# Production deploys require a named release authorization
cmd=$(jq -r '.tool_input.command' < /dev/stdin)
if [[ "$cmd" == *"deploy"* && "$cmd" == *"production"* ]]; then
  if [ -z "$RELEASE_APPROVAL" ]; then
    echo "Production deploys need a release authorization." >&2
    exit 2   # exit 2 blocks the action; the message goes to Claude
  fi
fi
exit 0

治理考量

hooks 就是那些审批门禁。门禁条件每一次都被强制执行，对所有人生效。放行与拦截的决定都带时间戳留痕。门禁同时也定义了什么才算「批准」——无论那是一张已获批的变更工单，还是发布经理的签署确认。

受监管企业的受管设置

下面是一份面向受监管企业的受管设置，由平台团队通过移动设备管理（MDM）或管理控制台下发。工程师无法编辑或覆盖其中任何一项设置：

json · managed settings 
{
  "permissions": {
    "deny": [
      "Read(.env*)", "Read(./secrets/**)",
      "WebFetch", "Bash(curl *)", "Bash(wget *)"
    ],
    "allow": [
      "Bash(git *)", "Bash(make build)",
      "Bash(make test)", "Bash(make lint)"
    ],
    "disableBypassPermissionsMode": "disable"
  },
  "allowManagedPermissionRulesOnly": true,
  "sandbox": {
    "enabled": true,
    "failIfUnavailable": true,
    "allowUnsandboxedCommands": false,
    "network": { "allowedDomains": ["git.internal.example.com", "registry.npmjs.org"] },
    "credentials": {
      "files": [
        { "path": "~/.ssh", "mode": "deny" },
        { "path": "~/.aws/credentials", "mode": "deny" }
      ],
      "envVars": [ { "name": "GITHUB_TOKEN", "mode": "deny" } ]
    }
  },
  "allowManagedHooksOnly": true,
  "disableSideloadFlags": true,
  "allowManagedMcpServersOnly": true,
  "strictKnownMarketplaces": [
    { "source": "github", "repo": "example-corp/approved-plugins" }
  ],
  "requiredMinimumVersion": "2.1.193"
}

用控制项的语言来说，这些设置分别做了什么：

  • permissions.deny 让密钥不进入 agent 的上下文，并阻断通过工具进行的任意出网。permissions.allow 则预先批准安全的内层循环，使拒绝清单不至于演变成审批疲劳。
  • disableBypassPermissionsMode 加上 allowManagedPermissionRulesOnly，意味着任何工程师、任何项目文件、任何命令行参数都无法放宽这些规则。
  • sandbox 覆盖权限机制覆盖不到的部分。在工具层面拒绝 WebFetch，并不能阻止一条 shell 命令连上网络；而 OS 级的域名允许清单则直接阻断出网——所以两者是在不同层次上强制同一个目标。failIfUnavailable 和 allowUnsandboxedCommands 把沙箱变成一项前置条件：沙箱无法初始化时 Claude Code 拒绝启动，而在沙箱内失败的命令不能拿到沙箱外重试。
  • credentials 处理的是拒绝规则漏掉的一种情形。permissions.deny 管的是 Claude 的文件工具，但一条沙箱内的 shell 命令默认仍可能读到 ~/.ssh 或 ~/.aws/credentials。这一段拒绝了那些读取，并从沙箱命令的环境中剥离所列的密钥。
  • allowManagedHooksOnly 意味着只有定义在受管设置中的 hooks 才会运行；用户级、项目级和本地设置中的 hooks 一律被阻断——包括上面那个独立的 .claude/settings.json 示例。要让本 play 的审批门禁保持强制生效，就得把它定义在受管文件自己的 hooks 段里。
  • disableSideloadFlags 和 strictKnownMarketplaces 意味着工程师机器上的任何 skill、agent、hook 或 MCP 服务，都来自组织已批准的插件市场，而不是来自某个家目录。市场允许清单控制什么可以被安装，而那些能为单次运行侧载插件、agent 或 MCP 配置的参数，会在启动时被拒绝。
  • allowManagedMcpServersOnly 让 agent 的工具面成为一份由平台团队掌管的允许清单。
  • requiredMinimumVersion 让低于已批准下限的版本无法启动，因此这些控制项是由一个组织确实评估过的构建版本来强制执行的。

Stage 5 部署

在 CI/CD 流水线内部以非交互方式运行 Claude Code，把执行过程沙箱化以便长时间运行的 agent 也能安全运行，通过 MCP 集成把部署能力暴露出来，并在 agent 真正需要之前就把各条回滚路径演练好。

发生了什么变化

传统做法AI 原生做法
流水线运行确定性脚本，任何需要判断的事都要等人：比如甄别那个不稳定的测试、写变更日志，或者搞清楚构建为什么坏了。部署与回滚是人在压力下照着执行的运行手册。 Claude 在流水线内部以非交互方式运行那些需要判断的步骤，在沙箱中、带受限作用域的凭据下执行。部署工具通过 MCP 暴露给 agent，因此那条写出并测试了变更的工作流，也能把它发布出去、并把它回滚回来——全部发生在组织按环境定义的门禁之内。

上手准备

前置条件：让 AI 进入 PR 评审闭环用 hooks 作为审批门禁

门禁必须先存在，自动化才谈得上加速通过它们。

基础设施：一个已安装 claude-code-action 的 CI 平台，或者任何能调用 claude -p 的执行器；通过 API 获得的模型访问权限，或在流量必须留在组织云合约内时走 Amazon Bedrock、Microsoft Foundry 或 Vertex AI；面向各部署目标的 MCP 服务；以及一份供 agent 作业使用、默认不持有任何常驻生产凭据的沙箱配置。

怎么执行

  1. 平台工程师从只读的判断类步骤开始。在流水线作业里用 claude -p 来甄别一次失败的构建、总结一个不稳定的测试，或者起草变更日志。
  2. 把写入类步骤加到既有门禁之后，用于修 lint、更新生成的文档，或通过 @claude 提及来处理评审意见这类活儿。agent 写出的任何东西都以 PR 的形式、经由分支保护抵达，agent 没有任何途径推送到 main。
  3. 执行过程是沙箱化的。agent 作业运行在容器中、受网络策略约束，使用短时效、受限作用域的令牌，且默认不持有生产凭据。
  4. 通过 MCP 暴露部署能力。部署、查状态和回滚成为工具，按环境限定作用域——于是 agent 的部署权力是一份允许清单，而不是一个带着凭据的 shell 脚本。
  5. 按环境分级自主程度。在开发环境，agent 自由部署。在生产环境，agent 准备好这次发布、由发布经理授权，并有一个 hook 强制那道生产门禁。预发布环境处在两者之间。
  6. 回滚应当是整条流水线中演练得最充分的路径：一条 agent 能够运行的单一命令，并且在预发布环境中被定期演练。闭合循环 play（Stage 6 维护）会在控制带被突破时调用这条回滚，所以它必须事先被证明可用。

治理考量

统摄性原则

agent 可以行动到生产门禁为止，但不能越过它。下面这些控制项强制该原则。

  • 分支保护把 agent 写出的任何东西都变成一个 PR，不存在直通 main 的路径。
  • 生产部署 hook 拦住这次发布，直到一位具名的发布经理授权。每一次非交互运行都以 agent 自己的身份行动，因此流水线日志把「agent 做了什么」与「触发它的那位工程师做了什么」区分开来。
  • 按环境划分的权限层级规定了 agent 在抵达门禁之前可以做到多少事。

怎么度量

领先指标

无需呼叫人工即被甄别处理的流水线失败占比，取自 CI/CD 流水线日志。

滞后指标

DORA（DevOps Research and Assessment）度量指标——CI 系统和部署工具本就在产出这些数据。

Stage 6 维护

13用指标闭合整个循环

前面每一个阶段都需要一个人来启动它，而 Stage 6 把重心转向让 Claude 自主运行以闭合这个循环。

举例来说，一个持续运行的监控 agent 可以在一张 bug 工单被提出之后，创建一份 intent.md，并让它流经需求、计划、构建、测试和评审各个环节。Stage 6 维护 以无人值守方式运行，各阶段之间设有一道独立的置信度门禁——可以是一项确定性检查，也可以是一个对抗性的评审 agent——由它决定上一阶段的产出是继续往下走，还是升级给人处理。

发生了什么变化

传统做法AI 原生做法
维护是一个被动的阶段。所有工单或事故都要等一个人来处理、来重新启动流程。凌晨三点触发的告警可能被漏掉，一张工单可能一直躺在待办里等人来捡，而如果又有别的火情烧起来，事后复盘的行动项可能根本到不了代码库。 一个触发器——控制带被突破、一张工单、一条频道消息，或者一个定时计划——在没有人介入的情况下唤起 Claude。Claude 做诊断，只经由受门禁约束的路径行动，并把它的发现写成 intent.md，随后这份产物流经上述各个阶段。人负责甄别与评审这些工作，而不再需要启动它们。

一个确定性脚本盯着生产环境，在控制带被突破时唤起 Claude。「监控突破」是这个自主循环模式的一个便于讲解的例子；而本阶段末尾的 Claude Tag（公开测试）一节，覆盖的是通过其他渠道抵达的工作。

上手准备

前置条件：intent.md由 Claude 加速的 PR 评审作为动作边界的 hooksCI/CD 的回滚路径

intent.md 为这个循环提供了一个可用于重新启动的结构化输出。以及由 Claude 加速的 PR 评审、作为动作边界的 hooks，还有 CI/CD 的回滚路径（最高自主层级会调用它）。

基础设施：一个检测脚本能够查询的指标存储（Prometheus、CI 系统的 API，或同类系统）；对仓库的读取权限；一条在 CI 中以非交互方式运行 Claude Code 的途径，或者用于接收 webhook 的服务所需的 Agent SDK。

怎么执行

  1. 服务责任人或平台工程师挑一个具有稳定滚动基线的指标，例如 CI 测试失败率、部署后 5xx 率，或 PR 周期时长。
  2. 他们编写检测脚本，通常是在滚动窗口上计算均值与标准差，并配合判异规则（Western Electric 规则或类似规则），使控制带既能捕捉突刺、也能捕捉缓慢漂移。该脚本纳入版本控制并有单元测试，且检测环节保持完全确定性，不涉及任何模型。
  3. 响应层级定义在纳入版本控制的配置里（下面的 bands.yaml）。在 1σ 时脚本只记录日志；在 2σ 时它以只读方式唤起 Claude 做诊断；在 3σ 时 Claude 可以行动，但只能通过开一个进入评审门禁的 PR，或者触发一份事先批准的运行手册。
  4. 触发层可以是 GitHub 或 GitLab 里的定时工作流、来自既有监控栈的 webhook，或者网络内部的一个 cron 作业。Claude 以无状态方式运行——要么作为 CI 执行器上的一个非交互步骤，要么作为沙箱容器中的一个 Agent SDK 服务——CI/CD play 覆盖了部署与模型访问的各种选项。正因为这次运行是无状态且非交互的，一个循环可以在无人启动的情况下开始和结束。
  5. agent 把它的诊断按 Stage 1 规划 的格式写成 intent.md，涵盖该异常及其证据、期望结果、受影响的系统，以及任何待解决的问题。从那里开始，这个发现像其他任何事项一样流经整条流水线。
  6. 服务责任人或值班工程师甄别这个队列，把面向产品的发现路由给产品负责人：立即修、排期、或者驳回。驳回会用于调优控制带，帮助降低噪声。
  7. 当一个修复上线时，为该事故补一个 eval（见持续 evals play），以确保此类问题今后被防住。

治理考量

层级边界由纳入版本控制的配置强制执行，同时权限设置与受管设置拒绝生产环境访问。唤起、发现项和甄别决定都带时间戳留痕。服务责任人甄别并批准发现项，由此产生的变更走正常的 PR 评审门禁，而 agent 可以触发的那些运行手册都是事先被批准过的。

怎么度量

领先指标

从控制带被突破，到一份 intent.md 进入甄别队列所花的时间，对比原先「从事故到复盘行动项」的时间。检测脚本的日志里有突破时间戳和事故的层级。

滞后指标

发现项最终变成已合入修复的占比（甄别队列对比实际 PR 历史），以及同类事故的重复发生次数——随着修复为 eval 套件补进用例，这个数字应当下降。

举例

  • 当 CI 测试失败率突破 3σ 时，agent 隔离那个不稳定的测试，或者开一个回退 PR，由评审门禁来定夺。
  • 当部署后 5xx 率突破 3σ 且时间窗内有一次部署时，agent 触发既有的回滚流水线。
  • 当 PR 周期时长触发某条漂移规则时，agent 为工程管理层写一份报告——这表明这套机制对流程类指标同样有效，不止适用于生产指标。

用 Claude Tag 让 Claude 值班

事故也可能通过其他途径抵达，比如 Slack 或 Microsoft Teams 这类职场沟通应用。事故的形态可能是晚上十点在某个事故频道里发出的一条「需要紧急修复」的 Slack 消息，而现在它可以被立即处理。Claude Tag（目前在 Slack 上公开测试）让 Claude 以自己的身份成为那些频道的成员，于是每一起新事故都有了一位第一响应者，而这次响应本身也成为循环的一部分，并成为未来事故可以调用的记忆。

对话和机构知识都留在频道里，频道中的任何人都可以引导并推进这次响应。任何团队成员都能实时验证假设、探索新方案、展开排查，而频道历史又进一步增强了可审计性。通过 MCP 访问权限，Claude 会验证该指标已回到基线并在讨论线中确认这一点，并把复盘写入一个纳入版本控制的经验教训文件，供未来的排查读取。

Claude Tag 承接的工作不止事故。通过 MCP 在一张工单上被标记，或者在频道里被问到时，Claude 以同样的方式甄别这项工作：一个小而边界清晰的修复以 PR 的形式经由评审门禁抵达，而任何更大的事项则被写成 intent.md 交给 Stage 1 规划——到这一步，这个循环就开始自己喂养自己了。
