MHS · Model Hardware Standard

Model Hardware Standard · Anthropic research preview

一份让 AI agent 安全操作物理设备的共享规范（shared specification）。它适用于任何具备可编程接口（programmable interface）的设备，把实验室与制造车间原本需要数周甚至数月的硬件集成压缩到数小时或数分钟；它是 model-agnostic 的，任何 agent harness 都能通过 MCP 等标准协议访问它。

Anthropic 官方公告 anthropic.com/news/model-hardware-standard-research-preview

01一句话定义

MHS = Model Hardware Standard，中文通用译法「模型硬件标准」——Anthropic 未做中文本地化，此译法为中文媒体沿用的事实译名，并非官方中文名。

MHS 是一份让 AI agent 安全操作物理设备的共享规范（shared specification）。

由 Anthropic 推出，适用于任何具备可编程接口（programmable interface）的设备。

定位与现状

维度结论说明
形态shared specification一份共享规范，而不是某个单独产品
阶段research preview研究预览，先开放给一批科研实验室与先进制造企业
开源状态尚未开源Anthropic 明确表示开源前还有工作要做；当前需申请加入 waitlist
适用范围可编程接口设备任何具备 programmable interface 的设备
模型耦合model-agnostic与模型无关，任何 agent harness 都能通过 MCP 等标准协议访问它
现在还不是「拿来就用」的阶段

MHS 处于 research preview，尚未开源，访问方式是申请加入 waitlist。Anthropic 表示在开源之前还有工作要做，并会把研究预览期的发现作为安全部署指引的一部分一并发布。

02它解决什么问题

三个叠在一起的问题：集成耗时、设备互不通信、没有统一方式让 agent 安全操作它们。

MHS 之前MHS 之后
在实验室或制造车间配置并集成硬件，通常要数周甚至数月。多数设备之间无法互相通信，需要专家逐个搭建定制集成。 MHS 把这类集成工作压缩到数小时或数分钟。设备与 agent 能跨网络互相发现并通信，中间不需要定制的「翻译器」程序。
即便设备连通了，也没有统一方式让它们与 AI agent 共享数据，或让 agent 安全地操作它们。 driver 自动生成的 reference file 告诉 agent：设备能测什么、能调什么、会强制执行哪些安全上限。

三层障碍

  1. 集成耗时。硬件的配置与集成按周、按月计，每一套装置都要专家动手做定制集成。
  2. 设备互不通信。多数设备之间无法互相通信，每加一台仪器就要再搭一次桥。
  3. 没有统一的 agent 接口。设备即使连上了，也缺少统一方式与 AI agent 共享数据，或让 agent 安全地操作它们。
机制

03核心机制四层

标准化 driver、标准格式的可发现性、设备自描述、三种控制通道。四层叠起来才构成 MHS。

标准化 driverLAYER 1

driver 是在操作系统与硬件设备之间做翻译的软件。MHS driver 用一套简单原语——read（如 "get temperature"）与 write（如 "set temperature"）——任何硬件都能理解并执行。

readget temperature · writeset temperature

标准格式的可发现性LAYER 2

让设备与 agent 能跨网络互相发现并通信，中间不需要定制的「翻译器」程序。这一层取代的正是过去那种「每两台设备之间手搓一个中间件」的做法。

设备自描述LAYER 3

driver 帮 agent 理解它从未见过的设备，提供那些光看代码看不出来的机器特性。原文的例子是机械臂的重量——这对安全操纵它很重要。

这类信息过去多存在纸质手册里、存在某个人的个人电脑里，或者只是默会知识。MHS driver 提供 tag，用户可以直接用自然语言把这些信息写进去：自己写，或者与一个「访谈式询问硬件配置」的 agent 对话完成。

driver 据此自动生成一份 reference file，记录设备的通用特性：

  • 能测什么
  • 能调什么
  • 会强制执行哪些安全上限

agent 靠这份文件就知道该如何操作设备。

三种控制通道LAYER 4

MCP、命令行界面（CLI）、代码文件（API）。三者协同，使跨多设备的编排可以通过单行代码完成。

MCP协议访问+ CLI命令行界面+ API代码文件→ 多设备编排单行代码

05agent 如何工作

高层监督与指挥，而不是每一步都亲自推理。长时任务与高速控制则交给 agent 生成的代码文件。

在高层监督并指挥

agent 接收各设备的运行数据，在高层监督并指挥工作：

  • 跨仪器排布步骤
  • 监控结果
  • 随条件实时调参

把 driver 命令串成代码文件

遇到长时任务、或者需要比在线推理更快地操作设备时，agent 可以把一个或多个设备的 driver 命令串成一个代码文件，让设备自行执行，无需 agent 每步都推理。

实测观察：Claude 会像科学家那样探索

Anthropic 的实测观察是：Claude 会以探索性方式与实验和硬件交互，很像科学家。原文给出的案例是激光对准：

  1. Claude 调整激光器。
  2. 通过摄像头观察调整如何移动了激光束。
  3. 反复迭代，以理解事件序列。
  4. 随后把学到的东西打包成一个代码文件，写出一个确定性脚本。
  5. 激光对准从此无需每步推理，整个过程可作为单条命令运行。
探索一次，之后确定性执行

先用推理摸清硬件的行为，再把结论沉淀成脚本——这样既拿到了理解，也拿到了速度。

06早期案例

research preview 参与方的自述，如实转述。以下 6 例来自官方公告。

生物制药 Genentech

把 MHS 用于 BCA 蛋白定量实验（测样本总蛋白浓度的标准流程）自动化的概念验证，需协调液体处理仪、机械臂与酶标仪。

学术实验室 华盛顿大学 Baker & Pinglay 实验室

博士生 Zihao Song 用 MHS 建了远程监控仪器的看板；做了 AI agent 监督的 qPCR（通过反复升降温复制目标 DNA 序列），agent 盯着扩增曲线并在恰当时机终止流程；还打通机械臂与液体处理仪，实现无碰撞的板转移。

学术实验室 卡内基梅隆大学（CMU）

用 MHS 跑系列稀释的剂量-反应实验，比此前约快三倍。由一个 AI agent 编排液体处理仪、酶标仪、机械臂与监控摄像头——这些设备分布在三台接口根本不兼容的电脑上。

研究机构 HHMI Janelia

多个显微成像项目在用 MHS 加速。Ahrens 实验室科学家 Virginie Ruetten（研究睡眠如何帮助身体从压力中恢复）用 MHS 统一并编排了一套此前需要七个不同厂商程序、彼此无共享接口的实验装置。

量子计算 QuEra Computing

用中性原子造量子计算机。用 MHS 让 AI agent 控制其量子机器内部的部分激光系统；agent 开发出一个控制器，能在 99.3% 的情况下无需人工干预就恢复激光的「锁定」——即激光必须保持的、用于与原子相互作用的超精密频率。

实验自动化 Tetsuwan Scientific

把 MHS 集成进其自动化生物实验平台 ResearchOS，编排 qPCR 工作流，用于表征加州 San Pedro Creek 污染状况的公民科学项目。

以上均为各方自述，效果数字（约三倍、99.3%）来自官方公告原文，未经独立复现。

08已知局限与安全

这部分是官方公告明确写出的边界，不宜省略或轻描淡写。

模型侧的局限

空间与物理推理存在局限，仍需专家监督

作为大语言模型，Claude 是通过文本与图像来认识物理世界的。

原文案例：Genentech 的研究者处理蛋白样本时，必须引导 Claude 认识到——样本起泡导致的错误是物理故障、不是软件 bug，只能通过恰当的物理修正来缓解。

覆盖面的局限

MHS 目前不支持缺少编程接口的硬件。Anthropic 正与此类设备的制造商合作，把 MHS driver 内建进去。

安全工作

  • Anthropic 正与首批合作方共同建立额外的安全评估，强化物理世界中 AI 使用的保护措施。
  • 正在制定一份物理安全路线图，以增强其安全防护政策与针对滥用风险的执行覆盖。
  • 开源 MHS 时，会把研究预览期的发现作为安全部署指引的一部分一并发布。

10与 MCP 的关系

先区分两层：公告原文写了什么，以及 Anthropic 员工对外怎么定调。

公告原文支持的三条事实

  • MHS 是 model-agnostic 的（与模型无关）。
  • 任何 agent harness 都能通过 MCP 等标准协议访问 MHS。
  • MCP 是 MHS 三种控制通道之一，另两种是命令行界面（CLI）与代码文件（API）。

「MCP 之于软件，MHS 之于硬件」这个类比

这个广为流传的类比不是媒体自创，而是 Anthropic 方面主动定调：Anthropic 的 Alek Kemeny 对 Bloomberg 表示「What MCP did for software, MHS will do for the hardware world」（经 Quartz 转引）；他对 Fortune 另称 MCP 是「AI 到软件连接的 USB」。CNBC 的报道则用 USB-C 作类比。此后该类比被各家报道普遍复用。

引用这个类比时的两点注意

其一，它出自员工受访表态与媒体转引，不是公告原文的表述，两者不宜混为一谈。其二，Kemeny 的原话经 Quartz 转引 Bloomberg，Bloomberg 原文在付费墙后未直接核验，严谨引用时应标注转引链条。

11外部视角与同期对照

本节内容全部来自官方公告之外的来源，性质与前面各节不同，逐条标注了它是谁的说法。

「这不就是又一个标准吗」——与既有标准的对比质疑

公告发布当天，Hacker News 主帖（136 分 / 62 评论）的讨论集中在一个问题上：实验室与工业自动化领域早已有 SiLA 2、OPC UA、ROS 2 等标准，MHS 是否只是重复发明。有用户给出了一张分层定位图，把 MHS 放在既有标准之上而非替代它们：

Hacker News 用户 randomblock1 给出的分层定位 
Agent
  ↕  MCP / CLI / code files
MHS
  ↕  vendor API / SCPI / OPC UA / ROS
CAN / Modbus / USB
  ↕
hardware

该图为社区用户的理解，非官方架构说明。

同一讨论中的其他观点：有人直言「这就是 OPC UA / SiLA，只是换成了 AI 与机器之间的语义」并配上 xkcd/927（关于「标准太多，于是我们再造一个统一标准」的经典调侃）；有人问它「与 ROS 2 的目标基本相同」；也有人称设备自描述「USB HID 早就做了」。ROS 官方 Discourse 上另有专帖讨论 MHS 与 ROS 2 的层次关系，一位 URML 维护者把 MHS 定位为「Layer-0 的驱动与描述标准，与 URDF/SDF 同族」。

这些都是个人观点，不是机构立场

上述对比与质疑目前只见于 Hacker News 评论与 ROS Discourse 的单个帖子，属发言者个人看法。未找到 SiLA Consortium 或 OPC Foundation 就 MHS 发表的任何官方立场，不要把社区观点当作机构表态引用。

治理层面的两条批评

  • 「标准未公开，却叫 standard」——有用户指出 USB、CAN 这类标准由厂商联盟共同制定、规范公开可读，而 MHS 当前需申请审批才能获取，质疑其称为「标准」的正当性。
  • 「先训练优势」——有用户认为 Anthropic 借研究预览期获得数月的提前期，可先用这些数据后训练自己的模型，从而在自己定义的赛道上领跑。

这两条同样来自 Hacker News 用户，是观点而非事实认定。Anthropic 在公告中自陈正在制定物理安全路线图、并会在开源前先建立安全评估。
